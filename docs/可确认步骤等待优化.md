# 可确认步骤的等待优化

按最新要求，仅在可靠读到就绪信号时缩短已有等待。保持操作顺序、标定坐标、联系人选择、点击次数、重试次数和原有兜底策略；无法确认的步骤保持原样。未引入新的截屏或 OCR 识别。

## 本次修改

`UiWait` 是一个小型等待辅助类：立即检查条件，随后每 200ms 检查；条件成立则提前调用原回调，始终无法确认则等到原截止时间再调用原回调。播放器的同步接口用同样方式在原 600ms 等待内检查，检查间隔为 100ms。检查不会执行动作，也不新增全局事件监听。

| 位置 | 可提前继续的证据 | 无法确认时 |
| --- | --- | --- |
| 微信搜索入口之后 | 当前微信搜索窗口已有可用输入框 | 保留原 2000ms 等待 |
| 微信搜索框、正文输入框之后 | 当前仍在微信，键盘中完整显示本步剪贴板内容，且文字位置覆盖原剪贴板点击坐标 | 保留原 900ms / 1400ms 等待 |
| 微信粘贴搜索词之后 | 输入框已有本次搜索词，目标联系人文字可见 | 保留原 2200ms 等待，不改变原结果点击方式 |
| 微信点击结果之后 | 当前聊天窗口已出现，聊天输入框和顶部目标名称可见 | 保留原 1500ms 等待 |
| 微信粘贴正文之后 | 输入框正文一致且发送按钮可见可用 | 保留原 900ms 等待 |
| 微信打开功能面板、通话弹层之后 | 下一步所需的面板/弹层控件组合可见可用 | 保留原 1200ms 等待 |
| 通用搜索输入失败后的重试准备 | 目标 App 的输入框已聚焦且可用 | 保留原 700ms 等待，旧版原生桥也按原时长等待 |
| 悟空搜索文字写入 | 输入框内容与本次查询一致且已聚焦、可用 | 保留原 700ms 等待 |
| 播放器控制栏 | 当前同一 App 中所需控制按钮可见可用 | 保留原 600ms 等待与原点击逻辑 |

微信进入前台后的 1400ms、手势后的 400/420ms 缓冲、返回步骤、发送后的等待、不可读界面的坐标流程、扫一扫/付款码、App 启动后的衔接、旧播放器选片及全屏串联等本次未改。它们没有足够可靠的现有就绪证据，或优化需要改动原流程。尤其 App 启动时可能仍暂时读到旧页面，不能仅凭同名控件出现就提前推进。

## 交付状态

只修改源码并人工核对调用关系。按要求未运行测试、未构建、未安装、未同步生成的网页和 APK 资源。实际收益取决于控件是否可读；微信节点不可读时，相关步骤仍按原来的时间执行，不能保证整条微信流程明显变快。

本次只优化表内可确认就绪的等待，其他流程保持原样。此前视频与语音优化的范围分别见对应说明。
